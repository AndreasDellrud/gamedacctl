# Release and Arch package process

## Outcome

Every pull request and main-branch push runs the release pipeline as a non-publishing dry run. A pushed version tag runs the identical build and, only after all validation succeeds, publishes a GitHub prerelease containing:

- `gamedacctl-VERSION-1-x86_64.pkg.tar.zst`
- `gamedacctl-VERSION.tar.gz`
- `PKGBUILD`
- `SRCINFO`
- `SHA256SUMS`

The Cargo source archive intentionally excludes raw USB captures and repository-internal agent and task metadata. `PKGBUILD` is generated from `packaging/arch/PKGBUILD.in` after that archive exists, so its source checksum is derived rather than manually copied. The Arch package is then built and tested from the checksum-pinned archive, not from the checkout.

## Continuous dry run

`.github/workflows/release.yml` runs on pull requests, pushes to `main`, version tags, and manual dispatch. Non-tag runs validate the complete repository, build and inspect the release bundle, verify its checksums, and retain it as a temporary GitHub Actions artifact for 14 days. They cannot create a release because the build job has only read access to repository contents.

For a manual dry run, open the workflow in GitHub Actions, choose **Run workflow**, leave **Publish a prerelease** disabled, and select the branch or commit to test. This is the preferred check before changing a version or creating a tag.

## Publishing

Prepare one release commit that updates the version in `Cargo.toml` and its corresponding `Cargo.lock` entry. Run `scripts/validate`, commit, and push that commit. After its main-branch dry run passes, create and push an annotated tag whose name exactly matches the Cargo version:

```bash
git tag -a v0.1.1 -m "gamedacctl 0.1.1"
git push origin v0.1.1
```

The workflow rejects a mismatched or non-semantic tag. A manual publishing dispatch is also allowed, but **Publish a prerelease** succeeds only when the selected workflow ref is the already-pushed matching version tag. The workflow never creates or moves a tag.

The publish job receives `contents: write` only after the read-only build succeeds. It creates a draft prerelease, attaches the verified bundle, downloads the assets back from GitHub, runs `sha256sum -c`, and only then publishes the draft as a prerelease. Release notes are generated by GitHub from changes since the previous release.

## Build environment and security

The build job uses a digest-pinned official Arch Linux `base-devel` container and the Rust version pinned by `mise.toml`. Cargo uses the committed lockfile; package build and tests use `--frozen`. The resulting `.BUILDINFO` records the resolved Arch package environment. The workflow's GitHub-maintained actions are pinned to full commit SHAs, checkout credentials are not persisted, pull-request code never receives a write token, and no signing secret is configured.

The Arch package itself is not cryptographically signed. Users must verify the published `SHA256SUMS`. Artifact signing or GitHub attestations require a separate reviewed trust and key-management design rather than silently adding a long-lived secret.

## Local fallback

The repository-owned build script is the manual fallback and the workflow implementation:

```bash
scripts/validate
mise exec -- scripts/build-release --output target/release-assets/vVERSION
```

The output directory must be empty. Add `--allow-dirty` only for a local development dry run; a publishable source archive must come from a committed clean tree. The script refuses root because `makepkg` must run as an unprivileged user. It validates source exclusions, package paths, binary version, a packaged CLI dry run, the desktop file, udev rule, shared-library resolution, package metadata, and every checksum.

## Failure and rollback

Failure in validation or packaging creates no GitHub release. Failure during upload or destination verification leaves a private draft rather than a public release. Inspect its assets and workflow log; delete only that draft if rerunning the same immutable tag:

```bash
gh release delete vVERSION --yes
```

Do not move a tag attached to a published release. Correct the problem in a new commit and version, then publish a successor. A published prerelease can be marked as superseded in its notes, but its binaries and checksums should remain available for provenance unless they contain a security or privacy defect.

## Omarchy plugin

The separate Omarchy adapter currently contains QML and a manifest but no compiled artifact. Omarchy installs it directly from its Git repository, so the controller release workflow does not mutate or publish the plugin repository. That repository should retain its own manifest validation on changes. Add a separate tag workflow only if Omarchy distribution begins consuming versioned release archives.
